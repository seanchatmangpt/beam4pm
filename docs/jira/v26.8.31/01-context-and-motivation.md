# Context and Motivation — v26.8.31

Status: `PARTIAL_ALIVE[GGEN_IGNITER_BASE_CAPABILITY_TESTING_ALIVE(~/ggen_igniter, 10 files, 37 tests, 0 failures), BEAM4PM_ADOPTION_UNKNOWN(zero beam4pm consumption of the newly-tested capability surface as of this doc)]`

## Mission

v26.8.31 exists to close a real, measured gap between what `ggen_igniter` (beam4pm's
Elixir-native manufacturing engine, vendored at `26.8.30` per `mix.lock`) can actually do and
what beam4pm actually asks it to do. This session tested that gap directly rather than reasoning
about it: it read `~/ggen_igniter`'s real source and doc state, found large parts of the base
`igniter` hex library (`~> 0.8`) had never been exercised by a single test anywhere in that repo,
and wrote 10 new real test files (37 tests, 0 failures, re-verified this session) driven against
real content from `~/ex4pm` — a differently-shaped ontology-driven umbrella project used as the
research lab, distinct from beam4pm the product — closing that testing gap for real, on disk, in
`~/ggen_igniter`.

That work answers "does this capability exist and work." It does not answer "does beam4pm use
it." As of this document, the answer to the second question is no: beam4pm's entire manufacturing
consumption of `ggen_igniter` is `scripts/igniter_sync.sh`, which invokes `mix ggen_igniter.sync`
three times for pure EEx templating over 31 `Ash.Resource` modules. Every capability the new
tests cover — AST-level code manipulation, project/dependency/config manipulation, and
refactoring codemods — is untouched by beam4pm today. v26.8.31 is the adoption-side charter: what
beam4pm should deliberately pull from a now-tested capability surface, and what it must not pull
until known defects in that surface are worked around.

## Why now

`CLAUDE.md` states beam4pm's source-authority doctrine plainly: `ontology.ttl`, `ggen.toml`,
`rebar.config`, `mix.exs`, `src/beam4pm.app.src`, and the vendored pack's templates are legitimate
hand-editable manufacturing inputs; anything carrying a `GENERATED by ggen ... Do not edit.`
header is not. `scripts/igniter_sync.sh` is itself listed among those legitimate inputs. That
doctrine already anticipates a second, Elixir-native manufacturing engine sitting alongside the
primary Rust ggen pipeline — the doctrine was never the limiting factor. The limiting factor was
that `ggen_igniter`'s own base library had a large, previously undocumented, previously untested
surface, and no one — human or LLM — had verified what it could safely do before this session.

Before this session, `~/ggen_igniter/docs/integrations/igniter/project-actuation.md` already
carried an honest gap marker in its own reference table: `Igniter.Project.Module` and
`Igniter.Code.*` were marked **NOT USED** in production. Production usage of any
`Igniter.Code.*` module was limited to `lib/ggen_igniter/doctor_fixes.ex`, and it was never
exercised by a test. `Igniter.Project.*` and `Igniter.Refactors.*` had zero usage anywhere in
`~/ggen_igniter` — lib or test. The doc named the gap; nothing before this session closed it.

## Four real constraints, not theoretical ones

The same testing that closed the coverage gap also surfaced four real defects in the base
`igniter` library (`0.8.3`), each reproduced against real content and each with an exact root
cause. These are not hypothetical risks to weigh someday — they are constraints that must be
respected the moment beam4pm adopts the corresponding capability:

1. **`Igniter.Project.Deps.add_dep/2,3` crashes with an uncaught `CaseClauseError`** when the
   target `mix.exs` inlines `deps: [...]` directly in `project/0` instead of a separate
   `defp deps do [...] end`. Root cause: `Igniter.Project.Deps.get_dep/2`'s `with ... else`
   fallback (`deps.ex:261-262`) returns a bare `nil` when `Igniter.Code.Function.move_to_defp/3`
   fails to find `:deps`/`0`, and `add_dependency/4`'s `case` (`deps.ex:60`) has no clause for
   that bare `nil`. Reproduced against real `~/ex4pm/apps/ex4pm_contracts/mix.exs`, which inlines
   deps that way. **Verified against beam4pm's own `mix.exs` this session: beam4pm uses the safe
   convention** — `project/0` calls `deps: deps()`, and `deps/0` is a separate `defp deps do
   [...] end` (`mix.exs:10,35`). This defect does not currently block beam4pm, but any future
   sub-app added to the umbrella must be audited for the same convention before
   `Igniter.Project.Deps` automation touches it.
2. **`Igniter.Project.MixProject.update/4`'s own documented example is broken for a real
   two-dot semver.** `{:code, quoted}` with a binary `quoted` is parsed as real Elixir source via
   `Sourceror.parse_string!/1` (`mix_project.ex:262-264`), not treated as an already-literal
   value, so the library's own doc example (a bare string like `"0.1.1"`) breaks for any real
   semver with two dots as plain source text. The verified workaround is `{:code,
   inspect(new_version)}`. beam4pm's current version fields (`mix.exs`: `version: "0.1.0"`;
   `src/beam4pm.app.src`: `{vsn, "0.1.0"}`) already have the two-dot shape this defect targets —
   any future ggen_igniter-driven version bump must use the `inspect/1` workaround, never the
   library's own bare-string example.
3. **`Igniter.Project.Application.add_new_child/2,3` cannot find an insertion point** when the
   target `start/2` inlines its child list directly into `Supervisor.start_link([], ...)` instead
   of binding `children = [...]` first. It degrades honestly — a real warning, no crash, no
   silent misapplication — but produces no change at all if the caller doesn't check
   `igniter.warnings`. Any beam4pm Application module intended to receive future
   ggen_igniter-driven child insertion must use the `children = [...]` binding convention.
4. **`Igniter.Refactors.Rename.rename_function/4` has two real bugs.** (a) It crashes with
   `ArgumentError` (`length(nil)`) on any parenless zero-arity function definition (`def name do
   ... end`), because Elixir's AST represents that shape's `args` as `nil` and
   `update_refs/7`'s `length(args) == arity` guard (`rename.ex:322-326`) doesn't handle it. (b) It
   silently skips renaming a guarded definition (`def name(x) when guard do`) — the function name
   sits inside a `:when`-wrapper AST node the rename pattern doesn't match — while still correctly
   renaming internal self-call sites, producing a real partial/inconsistent rename with no error
   surfaced. `rename_function` is not yet safe to run as an automated codemod over beam4pm's
   generated Erlang/Elixir/Gleam projections without a pre-check for both patterns.

## What beam4pm should do about it

Adopt the covered capabilities deliberately, one at a time, each gated by the matching constraint
above — not as a blanket upgrade of `scripts/igniter_sync.sh`. Concretely, this means: treat the
now-tested `Igniter.Project.*`/`Igniter.Code.*`/`Igniter.Refactors.*` surface as available
manufacturing-input tooling under beam4pm's existing source-authority doctrine (these are
manufacturing-time tools, exactly like `ggen_igniter` itself, never a runtime dependency of
generated code), pick specific manufacturing steps currently done by hand or not done at all where
one of these capabilities is a strict improvement, and add each adoption as its own scoped,
Chicago-tested change with the corresponding defect's workaround or pre-check built in from the
start. `docs/jira/v26.8.31/02-product-requirements-igniter-capability-expansion.md`,
`03-known-defects-and-mitigations.md`, and `04-jira-epics-stories-acceptance.md` carry that
work forward in detail; this document establishes only the why.
