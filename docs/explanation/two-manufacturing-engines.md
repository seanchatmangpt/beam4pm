# Two Manufacturing Engines

beam4pm's application source is not written by hand — it is manufactured by two
independent generators, run from the same ontology, producing outputs that must agree.
Understanding why there are *two* engines, rather than one, requires looking at what
each is actually good at, and how the repo proves they didn't drift apart.

## The split: Rust ggen/Tera vs. ggen_igniter/EEx

The primary engine is Rust ggen driving Tera templates, invoked by `just sync`
(`Justfile:12-15`: `rm -f ggen.lock; ggen sync run --dry-run; ggen sync run`). It reads
`ontology.ttl` — this repo's own RDF instance data, using the `bpm:RecordType` /
`bpm:Field` vocabulary defined in the vendored `vendor/ggen-marketplace/packs/
beam4pm-process-model-pack` pack (`ontology.ttl:1-15`) — and projects each admitted
record type into four language targets: Erlang (`src/`), Elixir (`lib/`), Gleam
(`gleam/src/beam4pm/`), and JSON Schema (`schema/*.schema.json`), plus generated
reference docs (`docs/reference/`). This is the engine CLAUDE.md describes at
lines 47-49.

The second engine is `ggen_igniter`, an Elixir-native generator invoked via
`scripts/igniter_sync.sh`, which internally runs `mix ggen_igniter.sync`
(`gate_m2_check.sh:100-102, 116`). It reads the same `ontology.ttl` but produces
something the Rust/Tera pipeline does not: `lib/beam4pm_ash.ex`, 31 `Ash.Resource`
modules, one per record type, each declaring `use Ash.Resource, domain:
BeamPM.Ash.Domain, data_layer: Ash.DataLayer.Ets` with an `attributes do ... end` block
and a `default_accept :*` create/read action pair. It also drives a family of
Elixir-side sync scripts — `receipt_chain_sync.sh`, `actuation_sync.sh`,
`process_governor_sync.sh`, the RF1-RF3 scripts, revenue/pro-capability scripts — each
named for the one module family it regenerates (`gate_m2_check.sh:100-141`,
CLAUDE.md:70-73).

## Why not one engine

The two engines aren't redundant paths to the same output — they solve different
problems. Rust/Tera is the cross-language projection engine: it has to emit
structurally different code for four target languages from one ontology (validating
`new_<type>/1` constructors in Erlang and Elixir, real typed records with
`option.Option` wrapping in Gleam, JSON Schema for the wire format). `ggen_igniter`
solves a narrower, Elixir-specific problem: producing idiomatic `Ash.Resource`
modules that plug into Ash's own domain/data-layer/action machinery, something that
only makes sense as an Elixir-native concern and doesn't generalize to Erlang or
Gleam output at all. Folding Ash generation into the Rust/Tera pipeline would mean
teaching a generic multi-language templating engine one target's idiosyncratic
framework conventions; keeping it separate lets each engine stay focused on the kind
of manufacturing it's actually suited for.

This split is visible in the generated-file headers themselves: Rust-ggen output
carries `GENERATED by ggen from the admitted bpm:RecordType graph. Do not edit.`
(e.g. `src/beam4pm_types_manifest.erl:1`), while `lib/beam4pm_ash.ex:1` carries
`GENERATED by ggen_igniter from the admitted bpm:RecordType graph. Do not edit.` —
same source ontology, explicitly different generator named in the marker.

## The cross-engine identity check: `beam4pm_types_manifest`

Because two independent engines read the same ontology, there's a real question:
do they actually agree on what the record types and fields *are*? The
`beam4pm_types_manifest` family answers this by existing in parallel, generator by
generator, as pure reflection modules — not constructors, not business logic, just
`record_names/0` and `fields/1` reporting what the ontology admitted.

- **Erlang** (`src/beam4pm_types_manifest.erl:1-16`): `record_names/0` returns a flat
  atom-list of admitted type names (line 14); `fields(RecordName)` is a per-type
  function-clause dispatch, e.g.
  `fields(account_discovery) -> [account_discovery_id, account_id, discovery_score, evidence_digest, observed_at];`
  (line 17). Its own moduledoc explicitly decouples it from `beam4pm_types.erl`'s
  `-record` definitions — it is schema-only reflection (lines 3-7).
- **Elixir** (`lib/beam4pm_types_manifest.ex:1-9`): `BeamPM.Types.Manifest` mirrors
  the same shape — `record_names/0` (line 6) returns the identical type list as
  atoms, and `fields/1` is one function head per type, e.g.
  `def fields(:account_discovery), do: [:account_discovery_id, :account_id, :discovery_score, :evidence_digest, :observed_at]`
  (line 9), with field lists matching Erlang's.

Because these two manifests are generated independently — Erlang by Rust/Tera, and
Elixir also by Rust/Tera but as a distinct output target — an ontology change that
only reaches one projection and not the other would show up immediately as a
manifest mismatch: different record counts, different field lists, different
required/optional flags. The manifests function as a live, checkable cross-engine
identity proof rather than a claim: if `ontology.ttl` says a field is required, both
`beam4pm_types_manifest.erl` and `beam4pm_types_manifest.ex` have to say so too, or
the generation pipeline itself is inconsistent.

The determinism gate `scripts/gate_m2_check.sh` extends this proof one level further:
it deletes every file carrying the `GENERATED by ggen` marker (found recursively
under `src, lib, test, gleam/src, gleam/test, schema, docs/reference` —
`gate_m2_check.sh:17`, deliberately not `-maxdepth 1` after a real prior bug where
`gleam/src/beam4pm/discovery.gleam` and `types.gleam` were silently missed by a
shallow scan, `gate_m2_check.sh:24-33`), regenerates by running *both* engines in
sequence — `ggen sync run` (Rust) then `igniter_sync.sh` and its dependent scripts
(Elixir) — and diffs the regenerated files' SHA-256 hashes against the pre-deletion
hashes (`gate_m2_check.sh:48-53, 96-147, 156-166`). A pass proves both engines are
pure functions of `(ontology.ttl, templates)` with no dependency on prior disk
state — not just that each engine is individually deterministic, but that running
them together, in the order the repo actually uses, reproduces byte-identical
output every time.

## What stays hand-authored on purpose

Not everything under `lib/` is manufactured. `lib/beam4pm_rust4pm.ex` (742 lines) has
no `GENERATED by ggen` header on line 1 — it's `defmodule BeamPM.Rust4PM do`,
confirmed hand-authored. Its moduledoc documents why: it's a BEAM-side wrapper over
the vendored `rust4pm` crate (`process_mining = "=0.6.2"`) compiled to
`wasm32-wasip1` and hosted via `wasmex`, framing and unpacking JSON over a documented
linear-memory ABI (`r4pm_alloc`/`r4pm_call`/`r4pm_dealloc`). Real process-mining
computation — XES import, DFG/alpha+++ discovery, PNML import, alignments, fitness —
happens inside the wasm module, not in ontology-generated code; there's no `bpm:`
record shape to project here, so neither engine has anything to manufacture. The
absence of a marker is itself the doctrine's signal (CLAUDE.md:26-33): check
first, edit only what isn't marked.
