Why Generated Code Lives in `src/`, Not `generated/`

Most code-generation setups draw a hard line in the filesystem: a `generated/`
directory (or `gen/`, or `.generated/`) holds machine output, everything else is
hand-written, and the boundary between them is a `.gitignore` entry or a directory
listing. beam4pm does not do this. There is no `generated/` directory anywhere in
this repository. Generated Erlang lives in `src/`, generated Elixir in `lib/`,
generated Gleam in `gleam/src/beam4pm/`, generated JSON Schema in `schema/`, and
generated reference docs in `docs/reference/` — the same directories a hand-authored
module in any of those languages would use. This page explains why, and what
discipline that choice requires in place of the one it gives up.

## The case against a `generated/` directory

A directory boundary is a strong, legible signal, but it buys that legibility at a
structural cost: it forces every consumer of the code — the compiler, the test
runner, other modules that import a type — to treat "generated" as a first-class
organizational axis, parallel to "what language" and "what domain." beam4pm's
generated output isn't a bolt-on; it *is* the application. CLAUDE.md describes the
repo as "a BEAM-first process-mining substrate whose application source is
manufactured entirely by ggen" — there's no meaningful "the real `src/` plus a
`generated/` annex," because for the record-type layer, the manufactured code is
the only implementation there is.

Putting manufactured Erlang in `src/gen/` instead of `src/` would also fragment
compilation and test discovery for no compiler-facing reason — `rebar3 eunit` and
`mix test` want ordinary language-idiomatic layout, not a generation-status
subdirectory layered on top of it. And a directory-level split invites exactly the
failure `gate_m2_check.sh` is built to catch: something manufactured that lives
*outside* the directory the tooling watches. That already happened once for real —
see below.

## Provenance is per-file, not per-directory

Instead of a directory boundary, beam4pm marks provenance with a literal string:
the first non-shebang line of a generated file reads `GENERATED by ggen ... Do not
edit.` `scripts/gate_m2_check.sh` encodes this as `MARKER="GENERATED by ggen"`
(gate_m2_check.sh:6, :16) and its `find_manufactured()` helper walks a fixed set of
directories — `src lib test gleam/src gleam/test schema docs/reference`
(gate_m2_check.sh:17) — checking the first three lines of every file
case-insensitively for that marker (`head -3 "$f" | grep -qi "$MARKER"`,
gate_m2_check.sh:44).

The case-insensitivity is not incidental hardening — it exists because the four
projections don't all spell the marker the same way. `docs/reference/beam4pm_types_reference.md`
uses a lowercase `*Generated by ggen ...*` in its Markdown comment form
(gate_m2_check.sh:39-43), so a case-sensitive grep would silently miss it. A
per-file marker has to tolerate that kind of surface variation across a Tera
template targeting Erlang, an EEx template targeting Elixir, and a Markdown
template targeting docs — a directory boundary would not have this problem, but it
would have the worse one described above.

The recursive-search choice in `SEARCH_DIRS` is itself the record of a real bug.
gate_m2_check.sh:24-33 documents that `gleam/src/beam4pm/discovery.gleam` and
`types.gleam` — nested one level under Gleam's own package-name convention, not
directly under `gleam/src/` — were silently never found, never deleted, and never
regenerated under an earlier `-maxdepth 1` scan. The fix wasn't to flatten Gleam's
directory layout to match the scanner's assumptions; it was to make the scanner
recurse. That ordering — trust the language's own conventions, adapt the tooling
to them — is the same instinct that keeps generated Erlang inside ordinary `src/`
rather than carving out a generation-status subtree: the directory structure
serves the language and the build, not the provenance question, because the
`GENERATED by ggen` marker already answers that question at finer grain than any
directory could.

One directory is explicitly *excluded* from the marker search for the opposite
reason: `gleam/build/` (gate_m2_check.sh:17-22) holds compiled Gleam artifacts, not
manufactured source. It's not marked because it isn't generated by ggen — it's
generated by the Gleam compiler from files that are. Conflating the two would make
`gate_m2_check.sh` delete and try to regenerate build output it has no template
for.

## Source-authority doctrine: what may and may not be hand-edited

The per-file marker isn't just a bookkeeping convention — it's the load-bearing
signal for an editing rule with no exceptions by directory. CLAUDE.md states it
plainly (CLAUDE.md:26-33): if a file's first non-shebang line reads `GENERATED by
ggen ... Do not edit.`, direct edits are refused, regardless of what directory it
sits in. If the generated output is wrong, the fix is upstream — in `ontology.ttl`
or in the vendored pack's templates under
`vendor/ggen-marketplace/packs/beam4pm-process-model-pack` — followed by a
regeneration (`rm ggen.lock && ggen sync run`).

Everything else is a legitimate manufacturing input, hand-editable by design:
`ontology.ttl` itself, `ggen.toml`, `rebar.config`, `mix.exs`,
`src/beam4pm.app.src`, the vendored pack's templates, docs that aren't themselves
marked generated, and the shell/Elixir sync scripts under `scripts/`
(CLAUDE.md:31-33). Notice what this list actually contains: `src/beam4pm.app.src`
sits in the same `src/` directory as dozens of generated `.erl` modules, and it is
hand-editable, because it carries no `GENERATED by ggen` marker. A directory-based
rule ("nothing in `src/` is hand-edited") would get this file wrong. A per-file
marker gets it right, because the marker is checked, not assumed from location.

The reasoning behind refusing edits to marked files isn't just "respect the
tool" — it's that `ontology.ttl` and the pack templates are the actual source of
truth, and a direct edit to generated output is a local patch that the next
`ggen sync run` silently discards, or worse, a divergence that a determinism check
would then flag as a false regression. `ontology.ttl` is explicit about its own
role: it states (ontology.ttl:1-15) that it is beam4pm's own RDF instance data
using the `bpm:RecordType` / `bpm:Field` vocabulary defined in the vendored pack,
not in the file itself — meaning even `ontology.ttl` is only half the input; the
templates that turn RDF individuals into Erlang, Elixir, Gleam, and JSON Schema
live in the pack. Editing generated code directly edits neither of those two real
inputs, so the edit has no persistence beyond the next sync.

## The determinism gate makes the doctrine falsifiable, not just declared

A per-file marker convention is easy to state and easy to let rot — a stray
generated file without the marker, or a hand-edit to a marked file that nobody
catches until the next sync silently reverts it. `scripts/gate_m2_check.sh` exists
to make the "generated code is a pure function of `(ontology.ttl, pack templates)`"
claim checkable rather than asserted. Its four-pass structure (gate_m2_check.sh:
48-166):

1. **Locate** every marked file across `SEARCH_DIRS` (lines 48-50).
2. **Hash** each one with sha256 before touching anything (lines 52-53).
3. **Delete** every marked file, `rm -f ggen.lock`, then regenerate through both
   engines — the Rust ggen/Tera pipeline (`ggen sync run`) and the Elixir-native
   `ggen_igniter`/EEx pipeline (`scripts/igniter_sync.sh`, then the RF1-RF3,
   receipt-chain, actuation, process-governor, and revenue/pro family scripts) —
   lines 96-147.
4. **Re-locate and re-hash** the same set of files (lines 156-158), then diff the
   before/after checksums (lines 160-166): a mismatch is a hard failure with a
   diff printed; an exact match is a PASS reporting the count of byte-identical
   manufactured files.

This is the practical payoff of per-file provenance over a directory boundary: the
gate doesn't need to know anything about directory layout except where to look
(`SEARCH_DIRS`) — it discovers exactly what's generated by the same marker the
editing doctrine uses, deletes exactly that set, and proves regeneration reproduces
it byte-for-byte. A directory-based scheme would let this gate be simpler (just
`rm -rf generated/`), but it would also let a stray unmarked generated file sit
outside the swept directory undetected — the same class of bug that motivated the
recursive-search fix in the first place, just moved from "wrong depth" to "wrong
root."

One operational wrinkle worth naming, because it's a case where the doctrine's
per-file granularity requires extra care rather than making everything free: two
hand-authored test files —
`test/beam4pm_actuation_k8s_test.exs` and
`test/beam4pm_process_governor_k8s_test.exs` — reference manufactured modules at
compile time. If they stayed in place during Pass 3's delete-then-regenerate
window, they'd get compiled against modules that briefly don't exist and fail with
`UndefinedFunctionError` (gate_m2_check.sh:69-77). The gate stashes them to a
`mktemp -d` directory before deletion and restores them via an `EXIT` trap
(gate_m2_check.sh:55-94, restore at line 153, trap cleared at line 154). This is
the cost of mixing hand-written and generated files in the same directories: the
tooling has to be aware of which un-marked files depend on marked ones, because
the filesystem itself won't tell it.

## Trade-off, stated plainly

Per-file marker provenance costs more per-file discipline than a directory
boundary would: every generated template has to actually emit the marker
correctly, every hand-written file has to actually not have one, and a script like
`gate_m2_check.sh` has to actually check content rather than trust a path. What it
buys is a filesystem layout that serves the four target languages and their own
tooling conventions — `rebar3`, `mix`, Gleam's package structure — without
bending any of them to accommodate a generation-status axis that has nothing to do
with how those tools expect to find code. The marker convention plus the
determinism gate together make the "don't hand-edit generated output" rule
enforceable per-file at exactly the granularity the doctrine needs, including the
case (`src/beam4pm.app.src` alongside generated `.erl` modules) where a
directory-level rule would get the wrong answer.
