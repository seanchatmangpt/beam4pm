# Getting Started with beam4pm

This tutorial takes you from a fresh clone to a fully manufactured, tested beam4pm
checkout. beam4pm's application source is not hand-written — it is generated by ggen
from `ontology.ttl`, so the first thing you'll do after cloning is run the
manufacturing pipeline, not write code.

By the end, you'll have run `just verify` successfully and know where to look next.

## 1. Clone with submodules

beam4pm vendors its ggen-marketplace pack (`vendor/ggen-marketplace/packs/beam4pm-process-model-pack`)
as a git submodule. Clone with `--recurse-submodules` so it comes down in one step:

```sh
git clone --recurse-submodules <this-repo-url>
cd beam4pm
```

If you already cloned without that flag, fetch the submodule separately:

```sh
git submodule update --init --recursive
```

This is exactly what the `just submodules` recipe runs (Justfile:7-9).

## 2. Run the full verify chain

The single command that takes a fresh checkout to a manufactured, tested state is:

```sh
just verify
```

This runs the `submodules sync lint_truth test` operator chain (Justfile:27-28), which is:

1. `git submodule update --init --recursive` (Justfile:7-9)
2. `rm -f ggen.lock; ggen sync run --dry-run; ggen sync run` (Justfile:11-15) — deletes
   the prior lockfile and regenerates every manufactured file from `ontology.ttl` plus
   the vendored pack's templates.
3. `bash scripts/gate_lint_truth.sh` (Justfile:22-25) — scans hand-authored `.md`/`.ex`/`.erl`
   files under `docs`, `README.md`, `CLAUDE.md`, `CONTRIBUTING.md` for banned
   overclaiming phrases.
4. `rebar3 eunit && mix test` (Justfile:17-20) — the Erlang and Elixir test suites.

If you prefer to run each step by hand, or want to see intermediate output:

```sh
git submodule update --init --recursive
rm -f ggen.lock && ggen sync run --dry-run && ggen sync run
bash scripts/gate_lint_truth.sh
rebar3 eunit
mix test
```

## 3. What output to expect

**During sync**, `ggen sync run` writes per-language projections into `src/` (Erlang),
`lib/` (Elixir), `gleam/src/beam4pm/` (Gleam), `schema/*.schema.json` (wire-format JSON
Schema), and `docs/reference/` (generated reference docs) — see CLAUDE.md:47-49. Every
file it writes carries a `GENERATED by ggen ... Do not edit.` marker as its first
non-shebang line.

**`bash scripts/gate_lint_truth.sh`** prints, on success:

```
GATE LINT-TRUTH: PASS -- N hand-authored files scanned, 0 findings
```

**`rebar3 eunit`** compiles every manufactured module under `src/*.erl` — for example
`beam4pm_discovery.erl`, `beam4pm_precision.erl`, `beam4pm_roundtrip.erl` — and runs
their EUnit suites.

**`mix test`** compiles `lib/*.ex` (both the primary-engine modules such as
`lib/beam4pm_discovery.ex`, `lib/beam4pm_codec.ex`, and the igniter-engine's
`lib/beam4pm_ash.ex`, `lib/beam4pm_actuation.ex`, `lib/beam4pm_process_governor.ex`,
`lib/beam4pm_receipt_chain.ex`) and runs every `test/*.exs` file — 29 test files in
total, covering discovery, codec, precision, roundtrip, ash, ai_contracts, billing,
entitlement, receipt_chain, actuation, process_governor, the rf1/rf2/rf3 rust4pm
Reactor families, revenue_economics/metering, and the `pro_*` capability suites.

A clean `just verify` run means: submodules present, ggen sync completed, no banned
overclaiming phrases in hand-authored docs, and both test suites green.

## 4. Understand what just got manufactured

Every file beam4pm ships falls into one of two categories, distinguished only by a
marker on the first line — never by which directory it lives in:

- **`GENERATED by ggen ... Do not edit.`** — output of the manufacturing pipeline.
  Never hand-edit these files directly; if something is wrong, fix `ontology.ttl` or
  the vendored pack's templates and re-run `just sync`.
- **Everything else** — legitimate hand-edit surfaces: `ontology.ttl`, `ggen.toml`,
  `rebar.config`, `mix.exs`, `src/beam4pm.app.src`, the vendored pack's templates,
  docs, and the `scripts/*.sh` sync scripts.

`ontology.ttl` (6980 lines) is beam4pm's own RDF instance data using the `bpm:`
vocabulary (`bpm:RecordType`, `bpm:Field`) defined by the vendored pack — CLAUDE.md
documents 31 record types manufactured into all four language projections (Erlang,
Elixir, Gleam, and the Ash resources at `lib/beam4pm_ash.ex`).

## 5. Try one targeted regeneration script (optional)

Instead of a full `just sync`, you can regenerate just one manufactured module family.
For example, to regenerate only the discovery/DFG family:

```sh
bash scripts/rf1_dfg_sync.sh
```

Each `scripts/<name>_sync.sh` script regenerates one specific family named by the
script (`igniter_sync.sh`, `receipt_chain_sync.sh`, `rf1_dfg_sync.sh`,
`rf2_conformance_sync.sh`, `rf3_ocel_sync.sh`, `actuation_sync.sh`,
`process_governor_sync.sh`, and others) — prefer the matching script over a blanket
`ggen sync run` when iterating on one ontology slice.

## Where to look next

- To confirm the manufacturing pipeline is truly deterministic (proves ggen is a pure
  function of `ontology.ttl` plus the pack templates, with no dependency on prior disk
  state), run the determinism gate: `bash scripts/gate_m2_check.sh`.
- To confirm the Erlang and Elixir wire codecs agree byte-for-byte, run:
  `bash scripts/roundtrip_check.sh`.
- To see a full fresh-clone workflow including discovery demos per language, run:
  `bash playground/playground.sh`.
