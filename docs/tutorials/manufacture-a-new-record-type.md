# Manufacture a New Record Type

## What you'll do

Add one new `bpm:RecordType` individual to `ontology.ttl`, run the manufacturing
pipeline, and observe the real Erlang, Elixir, and Gleam code it produces — ending
with a passing eunit test you write against your own generated constructor.

You will not hand-write any application source. Everything under `src/`, `lib/`, and
`gleam/src/` in this tutorial is produced by `ggen sync run` from the ontology you edit.

## Prerequisites

- A clone of this repo with submodules initialized (`vendor/ggen-marketplace` is a
  submodule providing the `bpm:` vocabulary and templates — CLAUDE.md:5-6).
- `ggen`, `rebar3`, and `mix` on your `PATH`.
- Familiarity with reading (not writing by hand) Erlang and Elixir.

## Step 1 — Look at an existing record type

Open `ontology.ttl` and find the `ocel_event` individual (ontology.ttl:24-58). This is
the shape every `bpm:RecordType` follows: a `bpm:recordName`, `bpm:recordDoc`, and a
`bpm:hasField` list of `bpm:Field` individuals, each with `bpm:fieldName`,
`bpm:fieldType`, `bpm:fieldDoc`, `bpm:fieldRequired`, and `bpm:fieldOrder`.

You'll model your new type on this same shape.

## Step 2 — Add a new record type individual

We'll add `queue_alert`: a small record noting that a queue crossed a depth threshold.
Open `ontology.ttl` and add the following block near the end of the file (after the
last `bpm:RecordType` individual, before any `b4pe:` section that starts around line
2400 — keep it inside the core `bpm:` block, not the billing/entitlement extension):

```turtle
bpm:queue_alert a bpm:RecordType ;
    bpm:recordName "queue_alert" ;
    bpm:recordDoc "Raised when a queue's depth crosses an alert threshold." ;
    bpm:hasField (
        [ a bpm:Field ;
          bpm:fieldName "queue_name" ;
          bpm:fieldType "string" ;
          bpm:fieldDoc "Name of the queue that triggered the alert." ;
          bpm:fieldRequired true ;
          bpm:fieldOrder 1 ]
        [ a bpm:Field ;
          bpm:fieldName "depth" ;
          bpm:fieldType "integer" ;
          bpm:fieldDoc "Observed queue depth at alert time." ;
          bpm:fieldRequired true ;
          bpm:fieldOrder 2 ]
        [ a bpm:Field ;
          bpm:fieldName "threshold" ;
          bpm:fieldType "integer" ;
          bpm:fieldDoc "Configured alert threshold that was crossed." ;
          bpm:fieldRequired true ;
          bpm:fieldOrder 3 ]
    ) .
```

Save the file.

## Step 3 — Run the sync

From the repo root:

```sh
just sync
```

This runs `rm -f ggen.lock; ggen sync run --dry-run; ggen sync run` (Justfile:11-15).
The dry run reports what would change; the real run regenerates every manufactured
file whose inputs (the ontology graph plus the vendored pack's templates) changed —
including the manifest files that list every admitted record type.

## Step 4 — Observe the Erlang output

Open `src/beam4pm_types_manifest.erl`. Its first line is the marker:

```erlang
%% GENERATED by ggen from the admitted bpm:RecordType graph. Do not edit.
```

`record_names/0` (src/beam4pm_types_manifest.erl:14) now includes `queue_alert` in its
returned atom list, and `fields/1` (src/beam4pm_types_manifest.erl:17 onward) has a new
clause:

```erlang
fields(queue_alert) -> [queue_name, depth, threshold];
```

Look for your new record's constructor in `src/beam4pm_types.erl` — a validating
`new_queue_alert/1` returning `{ok, Record}` or `{error, {missing_field, Field}}`,
following the same shape CLAUDE.md documents for every generated Erlang record type.

## Step 5 — Observe the Elixir and Gleam output

`lib/beam4pm_types_manifest.ex` (marker at line 1, same convention) gains a matching
`:queue_alert` entry in `record_names/0` and a new function head:

```elixir
def fields(:queue_alert), do: [:queue_name, :depth, :threshold]
```

`gleam/src/beam4pm/types.gleam` gains a real typed record, not just reflection
metadata:

```gleam
pub type QueueAlert {
  QueueAlert(queue_name: String, depth: Int, threshold: Int)
}
```

All three projections were produced from the single ontology edit in Step 2 — no
per-language code was written by hand.

## Step 6 — Write a passing eunit test

Create `test/beam4pm_queue_alert_test.erl`:

```erlang
-module(beam4pm_queue_alert_test).
-include_lib("eunit/include/eunit.hrl").

new_queue_alert_success_test() ->
    {ok, Alert} = beam4pm_types:new_queue_alert(#{
        queue_name => <<"orders">>,
        depth => 120,
        threshold => 100
    }),
    ?assertEqual([queue_name, depth, threshold],
                 beam4pm_types_manifest:fields(queue_alert)),
    ?assert(is_map(Alert) orelse is_tuple(Alert)).

new_queue_alert_missing_field_test() ->
    Result = beam4pm_types:new_queue_alert(#{queue_name => <<"orders">>}),
    ?assertMatch({error, {missing_field, _}}, Result).
```

This file has no `GENERATED by ggen` marker — it lives in `test/`, one of the
directories `gate_m2_check.sh` scans (line 17), but hand-written test files without
the marker are never treated as manufactured output; only files carrying the marker
string are swept.

## Step 7 — Run it

```sh
rebar3 eunit --module=beam4pm_queue_alert_test
```

If `new_queue_alert/1` rejects an unrecognized key shape, check the actual field-key
convention the generated constructor for a neighboring type (e.g.
`beam4pm_types:new_ocel_event/1`) expects, and match it — the generated code, not this
tutorial, is the source of truth for the exact map-key contract.

A passing run confirms your round trip: one ontology edit → three real generated
language projections → one real passing test against the generated Erlang
constructor and manifest.

## What you did

You extended `ontology.ttl` — a legitimate hand-edit target per the doctrine below —
and let `ggen sync run` regenerate `src/`, `lib/`, and `gleam/src/` from it. You never
touched a `GENERATED by ggen` file directly.
