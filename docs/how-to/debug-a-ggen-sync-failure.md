# How to Debug a ggen Sync Failure

This recipe covers diagnosing a failed `ggen sync run` or `scripts/igniter_sync.sh` invocation:
reading the refusal, deciding whether the file in question is generated or a legitimate
manufacturing input, and picking the right fix surface.

## Before you touch anything: is the file generated?

Never hand-edit a file whose first non-shebang line carries the marker
`GENERATED by ggen ... Do not edit.` — this holds regardless of which directory the file
lives in (CLAUDE.md:26-30).

```sh
head -3 path/to/suspect/file
```

The check is case-insensitive on purpose: `docs/reference/beam4pm_types_reference.md` uses a
lowercase `*Generated by ggen ...` header, which `scripts/gate_m2_check.sh:39-46`'s
`find_manufactured()` matches via `head -3 "$f" | grep -qi "$MARKER"`.

If the marker is present, the fix belongs upstream:

- Wrong field, type, or doc string → edit `ontology.ttl` (the `bpm:RecordType` /
  `bpm:Field` individuals), then regenerate.
- Wrong template shape/structure → edit the vendored pack's templates under
  `vendor/ggen-marketplace/packs/beam4pm-process-model-pack`.
- Then re-sync: `rm -f ggen.lock && ggen sync run --dry-run && ggen sync run`
  (Justfile:11-15).

If the marker is **absent**, the file is a legitimate hand-edit surface. CLAUDE.md:31-33 names
the standing list: `ontology.ttl`, `ggen.toml`, `rebar.config`, `mix.exs`,
`src/beam4pm.app.src`, the vendored pack's templates, docs, and `scripts/*`.

## Reading a sync failure

### `ggen sync run` fails outright

Run it directly to see the raw error:

```sh
rm -f ggen.lock && ggen sync run --dry-run && ggen sync run
```

A dry-run failure usually means `ontology.ttl` doesn't parse or validate against the pack's
`bpm:` vocabulary shape — check the individual you last edited for a missing `bpm:fieldName`,
`bpm:fieldType`, or `bpm:fieldOrder` (see the `ocel_event` example at ontology.ttl:24-58 for
the expected shape: a `bpm:RecordType` with `bpm:recordName`, `bpm:recordDoc`, and
`bpm:hasField` listing `bpm:Field` individuals).

### `scripts/igniter_sync.sh` fails during `mix compile --warnings-as-errors`

This is the second engine (`ggen_igniter` / EEx), invoked separately from the Rust ggen
pipeline (CLAUDE.md:56-59, gate_m2_check.sh:100-102, 116). If it fails mid-compile it is
usually because a downstream module referencing `lib/beam4pm_ash.ex` hasn't been regenerated
yet, or a dependent sync ran out of order.

**Ordering matters.** `scripts/gate_m2_check.sh:100-109` documents the real constraint:
`receipt_chain_sync.sh` renders `beam4pm_receipt_chain.ex` first and then internally re-runs
`actuation_sync.sh` and `process_governor_sync.sh` itself. Calling those two scripts directly
in addition to `receipt_chain_sync.sh` races a second `mix compile --warnings-as-errors`
against a `ReceiptChain` module that hasn't been regenerated yet — run
`receipt_chain_sync.sh` alone and let it drive the other two.

### `FM-WRITE-005` and other file-write refusal codes

A refusal code surfacing from either engine on a write attempt means the target write path
did not match what the engine expected to own — most commonly, an attempt to write into a
path whose existing content doesn't carry the `GENERATED by ggen` marker the engine expects
to overwrite, or a path outside the engine's configured output roots. Treat any such refusal
the same way as a manual check: run `head -3` on the target path per the check above. If the
marker is missing, the refusal is protecting a hand-authored file — don't force the write;
instead confirm the ontology/template change is targeting the right output location. If the
marker is present but the write is still refused, the failure is upstream (a template or
ontology defect), not a permissions problem — regenerate via `just sync` after fixing the
ontology/template rather than editing the write target.

## Running the determinism gate to confirm a fix actually landed

After any ontology or template change, `scripts/gate_m2_check.sh` is the authoritative check
that ggen is a pure function of `(ontology.ttl, pack templates)`:

```sh
bash scripts/gate_m2_check.sh
```

It deletes every file it finds carrying the `GENERATED by ggen` marker under
`src, lib, test, gleam/src, gleam/test, schema, docs/reference` (recursively — a prior
`-maxdepth 1` scan missed `gleam/src/beam4pm/discovery.gleam` and `types.gleam`, per
gate_m2_check.sh:24-33), regenerates via the full sync chain (Rust ggen, then
`igniter_sync.sh`, `receipt_chain_sync.sh`, the RF1-RF3 family, revenue/pro scripts —
gate_m2_check.sh:96-147), and diffs sha256 checksums before/after.

**Failure output** looks like:

```
GATE M2: FAIL -- regenerated output differs from the deleted originals
```

followed by a diff of the sorted `sha256sum` listings on stderr, exit code 1
(gate_m2_check.sh:160-166). This means either ggen itself is non-deterministic, or an
ontology/template edit wasn't reflected consistently across every consuming template —
re-check the edit against every language projection (Erlang, Elixir, Gleam, JSON Schema)
rather than just the one you were looking at.

It can also fail mid-run, non-gracefully, if any `scripts/*_sync.sh` invocation exits
nonzero (e.g. an `igniter_sync.sh` compile failure) — the script runs under `set -euo
pipefail` (gate_m2_check.sh:13), so the whole gate aborts immediately. An `EXIT` trap still
restores the two hand-authored test files it stashes
(`test/beam4pm_actuation_k8s_test.exs`, `test/beam4pm_process_governor_k8s_test.exs`) even on
an abort (gate_m2_check.sh:80-91), so a failed gate run never leaves those test files
missing.

## Quick decision checklist

1. `head -3 <file>` — marker present? Fix `ontology.ttl` or the pack template, not the file.
2. Marker absent — the file is a legitimate hand-edit surface per CLAUDE.md:31-33.
3. Re-sync: `rm -f ggen.lock && ggen sync run --dry-run && ggen sync run`.
4. If `igniter_sync.sh` fails specifically, check you didn't call `actuation_sync.sh` or
   `process_governor_sync.sh` directly alongside `receipt_chain_sync.sh`.
5. Confirm with `bash scripts/gate_m2_check.sh` before considering the fix done.
