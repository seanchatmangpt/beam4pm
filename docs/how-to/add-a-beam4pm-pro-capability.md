# Adding a New BeamPM.Pro.* Capability Module

## Before you start

`beam4pm_pro` capabilities are ggen_igniter-manufactured static modules, not
hand-written Elixir. Each one lives at `lib/beam4pm_pro_<name>.ex`, carries the
`GENERATED by ggen ... Do not edit.` header, and is produced by its own
`scripts/pro_<name>_sync.sh` script rather than a blanket `ggen sync run`. This
recipe follows the real pattern used by `BeamPM.Pro.Tenancy`
(`lib/beam4pm_pro_tenancy.ex`), `BeamPM.Pro.OcpmDiscovery`
(`lib/beam4pm_pro_ocpm_discovery.ex`), and `BeamPM.Pro.Simulation`
(`lib/beam4pm_pro_simulation.ex`).

## Steps

### 1. Write the ggen_igniter EEx template for the module

Add a template alongside the existing pro-capability templates in the vendored
pack (`vendor/ggen-marketplace/packs/beam4pm-process-model-pack`), following
the same structure the three existing modules use: a purpose comment block at
the top of the file (the doc header, e.g. `lib/beam4pm_pro_tenancy.ex:1-27`,
`lib/beam4pm_pro_ocpm_discovery.ex:1-27`, `lib/beam4pm_pro_simulation.ex:1-17`)
naming what the module does and, where relevant, what it deliberately does
*not* do — `BeamPM.Pro.OcpmDiscovery` documents "no OC-Petri-net synthesis"
and exposes a `gaps/0` function listing unimplemented extensions
(`lib/beam4pm_pro_ocpm_discovery.ex:87`); `BeamPM.Pro.Simulation` does the same
for "no discrete-event/throughput simulation" (`lib/beam4pm_pro_simulation.ex:119`).
If your new capability has known scope boundaries, give it a `gaps/0` too.

Public functions should be typed and documented the same way — see
`BeamPM.Pro.Tenancy.authorize/3` (`lib/beam4pm_pro_tenancy.ex:59`) and
`BeamPM.Pro.Simulation.reachable_from/2` (`lib/beam4pm_pro_simulation.ex:47`)
for the level of detail expected (typespec, doc, real logic — e.g. `has_cycle?/1`
is a real DFS with a recursion stack, not a stub).

### 2. Write the matching EExtest template

Each pro-capability module has a corresponding ExUnit test file manufactured
alongside it. Follow the existing test naming convention:
`test/beam4pm_pro_tenancy_test.exs`, `test/beam4pm_pro_ocpm_discovery_test.exs`,
`test/beam4pm_pro_simulation_test.exs` — your new module gets
`test/beam4pm_pro_<name>_test.exs`. Cover the real return shapes documented in
the module (e.g. `{:error, {:insufficient_role, roles, capability}}` for
`Tenancy.authorize/3`, a `MapSet` for `Simulation.reachable_from/2`) with
Chicago-style state-based assertions over real function calls — no mocking.

### 3. Add ontology facts (if the capability needs configuration data)

If the new module needs individuals (like `bpma:AdmittedActuation` facts drive
`actuation_sync.sh`), add the relevant RDF instance data to `ontology.ttl`
following the existing `bpm:RecordType`/`bpm:Field` pattern documented in
`CLAUDE.md`. A purely-structural module (no per-instance data, like
`Simulation` or `OcpmDiscovery`) may not need this step.

### 4. Write `scripts/pro_<name>_sync.sh`

Copy the shape of an existing pro sync script (e.g.
`scripts/pro_tenancy_sync.sh`, `scripts/pro_ocpm_discovery_sync.sh`, or
`scripts/pro_simulation_sync.sh`) and point it at your new template. Each of
these scripts is a single-purpose regeneration entry point named after the
module it produces — this is the same convention `receipt_chain_sync.sh`,
`rf1_dfg_sync.sh`, and the other named `scripts/*_sync.sh` scripts follow.

### 5. Register the script in `gate_m2_check.sh`

The determinism gate (`scripts/gate_m2_check.sh`) runs every `pro_*_sync.sh`
script explicitly by name in Pass 3, alongside `receipt_chain_sync.sh`,
`rf1_dfg_sync.sh`/`rf2_conformance_sync.sh`/`rf3_ocel_sync.sh`, and the revenue
sync scripts (`scripts/gate_m2_check.sh:135-141`). Add your new
`pro_<name>_sync.sh` invocation to that block so the gate exercises it on
every determinism check — a script that exists but isn't called from
`gate_m2_check.sh` won't be proven to reproduce byte-identically.

### 6. Run the sync

```sh
bash scripts/pro_<name>_sync.sh
```

This regenerates `lib/beam4pm_pro_<name>.ex` (and its test file) from the
template. Confirm the generated file carries the
`GENERATED by ggen ... Do not edit.` marker as its first non-shebang line.

### 7. Run the tests

```sh
mix test test/beam4pm_pro_<name>_test.exs
```

Once the individual test passes, run the full suite to confirm nothing else
regressed:

```sh
mix test
```

### 8. Verify determinism

Run the full gate to confirm your new script reproduces byte-identically and
doesn't disturb the other manufactured modules:

```sh
bash scripts/gate_m2_check.sh
```

This deletes every `GENERATED by ggen`-marked file (including your new one),
regenerates everything — Rust ggen pipeline, `igniter_sync.sh`,
`receipt_chain_sync.sh`, the RF1-RF3 scripts, revenue scripts, and all
`pro_*_sync.sh` scripts including yours — and diffs before/after checksums.
