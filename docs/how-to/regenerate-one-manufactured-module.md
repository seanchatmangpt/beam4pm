# Regenerating One Manufactured Module Family

Use this recipe when a single manufactured module (for example `beam4pm_discovery`,
`BeamPM.ReceiptChain`, or `BeamPM.Actuation`) needs to be rebuilt after an `ontology.ttl`
or pack-template edit, and you want to avoid the cost and blast radius of a full
`scripts/gate_m2_check.sh` sweep.

## When to use this vs. `gate_m2_check.sh`

`gate_m2_check.sh` deletes *every* file carrying the `GENERATED by ggen` marker across
`src, lib, test, gleam/src, gleam/test, schema, docs/reference`, regenerates all of them,
and diffs before/after checksums — it is the determinism proof, not a routine dev-loop
tool. It is also destructive mid-run: it stashes two hand-authored test files
(`test/beam4pm_actuation_k8s_test.exs`, `test/beam4pm_process_governor_k8s_test.exs`) to a
`mktemp -d` directory and restores them via an `EXIT` trap, because they reference
manufactured modules that don't exist for the window between deletion and regeneration.

For an ordinary iteration on one module family, use the matching `scripts/<family>_sync.sh`
script instead — it only touches the files that one family owns.

## Steps

1. **Identify the right script.** Match the module name to its sync script:

   | Module / family | Script |
   |---|---|
   | `beam4pm_discovery` / `BeamPM.Discovery` | regenerated by the primary `ggen sync run` pass (Rust/Tera engine) — see step 2 below |
   | `lib/beam4pm_ash.ex` (31 `Ash.Resource` modules) | `scripts/igniter_sync.sh` |
   | `BeamPM.ReceiptChain` | `scripts/receipt_chain_sync.sh` |
   | `BeamPM.Actuation` | `scripts/actuation_sync.sh` |
   | `BeamPM.ProcessGovernor` | `scripts/process_governor_sync.sh` |
   | `BeamPM.RF1.DfgDiscovery` | `scripts/rf1_dfg_sync.sh` |
   | `BeamPM.Rf2Conformance` | `scripts/rf2_conformance_sync.sh` |
   | `BeamPM.RF3Ocel` | `scripts/rf3_ocel_sync.sh` |
   | `BeamPM.Revenue.Economics` | `scripts/revenue_economics_sync.sh` |
   | `BeamPM.Revenue.Metering` | `scripts/revenue_metering_sync.sh` |
   | `docs/reference/types/<record_name>.md` (per-record-type docs) | `scripts/pro_type_pages_sync.sh` |
   | `BeamPM.Pro.*` modules | the matching `scripts/pro_*_sync.sh` |

2. **If the module is one of the core Erlang/Elixir/Gleam/JSON-Schema projections**
   (`src/*.erl`, `lib/*.ex` outside `beam4pm_ash.ex`, `gleam/src/beam4pm/*.gleam`,
   `schema/*.schema.json`, `docs/reference/*` outside the per-type fan-out), it comes from
   the primary Rust ggen engine, not a per-module script. Regenerate the whole primary pass
   with:

   ```sh
   rm -f ggen.lock
   ggen sync run --dry-run
   ggen sync run
   ```

   This is `just sync` (Justfile:12-15). It is not scoped to one module — `ggen sync run`
   re-projects from `ontology.ttl` in one pass — but it does not touch the second,
   Elixir-native `ggen_igniter` engine's outputs (`lib/beam4pm_ash.ex` and the
   `pro_*`/`actuation`/`receipt_chain`/`rf*` family), so it is still narrower than
   `gate_m2_check.sh`.

3. **If the module belongs to the `ggen_igniter` engine**, run only its own script, e.g.:

   ```sh
   bash scripts/receipt_chain_sync.sh
   ```

   **Ordering constraint:** `scripts/receipt_chain_sync.sh` renders `BeamPM.ReceiptChain`
   first and then internally re-runs `scripts/actuation_sync.sh` and
   `scripts/process_governor_sync.sh` itself. Do not call `actuation_sync.sh` or
   `process_governor_sync.sh` directly in the same pass as `receipt_chain_sync.sh` — a
   second, independently-triggered `mix compile --warnings-as-errors` would race a
   not-yet-regenerated `ReceiptChain` module.

4. **Verify the edited ontology facts actually changed the output.** Diff the regenerated
   file against its previous committed state:

   ```sh
   git diff -- lib/beam4pm_ash.ex
   ```

   (substitute the actual output path for the family you regenerated).

5. **Confirm the `GENERATED by ggen` marker is still the first non-shebang line** of every
   file the script touched — this is what `gate_m2_check.sh` checks for at full-sweep time
   (`head -3 "$f" | grep -qi "GENERATED by ggen"`), so a template change that drops the
   marker will silently fall out of the gate's coverage rather than fail loudly here.

6. **Run the narrowest test suite that covers the family**, not the full `just test`, when
   iterating:

   ```sh
   rebar3 eunit --module=beam4pm_discovery
   mix test test/beam4pm_receipt_chain_test.exs
   ```

7. **Before merging**, still run the full determinism gate at least once —
   `bash scripts/gate_m2_check.sh` — to prove the targeted regeneration didn't leave the
   repo in a state where a full-sweep regeneration would produce different bytes.
