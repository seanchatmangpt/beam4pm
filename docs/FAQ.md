# FAQ

## Why can't I just edit `src/beam4pm_types.erl` directly?

Because it's ggen-manufactured output. The file starts with `%% GENERATED by ggen
from the admitted bpm:RecordType graph. Do not edit.` — every record, type spec,
and constructor in it is projected from `ontology.ttl` through the ggen pack
templates, not hand-authored. An edit made directly in the file survives only
until the next `ggen sync`, at which point it is silently overwritten and the
fix is lost. If a field is wrong, missing, or mistyped, the fix belongs in
`ontology.ttl` (change the admitted `bpm:RecordType` shape) or in the pack
templates that project it into Erlang. See `CONTRIBUTING.md` for the exact
workflow.

## Where does generated output live? Why is there no `generated/` directory?

There isn't one, deliberately — a top-level `generated/` directory is a
ggen antipattern this repo refuses. Manufactured code lives in the same
`src/`, `lib/`, `test/`, `gleam/`, `schema/`, and `docs/reference/`
directories hand-authored code would use; provenance is signalled
per-file by the `GENERATED by ggen ... Do not edit.` header (see the
previous question), never by directory placement. Both engines write
straight into those directories: the primary Rust `ggen`/Tera pipeline and
the second, Elixir-native `ggen_igniter`/EEx engine (see CLAUDE.md's
"Manufacturing pipeline" section).

Erlang, Elixir, Gleam, and Ash are all real today, each a full language
projection of the same admitted `bpm:RecordType` graph: Erlang in `src/`,
Elixir in `lib/`, Gleam in `gleam/src/beam4pm/`, and Ash (31
`Ash.Resource` modules, `lib/beam4pm_ash.ex`) via the `ggen_igniter`
engine specifically. None of the four are future work — see CLAUDE.md's
"Four language projections" for what's disclosed as still partial in
each (e.g. Gleam has no wire-codec leg yet).

## What does "ggen-only" actually guarantee today?

Only that the admitted record types' Erlang and Elixir type/struct
definitions and their constructors are manufactured, not hand-authored. As of
this slice that's 31 record types (`alignment_move`, `dfg_edge`, `ocel_event`,
`ocel_object`, `ocel_relationship`, `petri_arc`, `petri_place`,
`petri_transition`) admitted into the `bpm:RecordType` graph in `ontology.ttl`,
each projected into a `-record(...)` / `-type ...() :: #...{}` pair with a
`new_*/1` constructor in `src/beam4pm_types.erl`, and the
matching Elixir struct in `lib/beam4pm_types.ex`. It does not
yet mean the whole `beam4pm`/`beam4pm_pro` product is ggen-manufactured —
business logic, process-mining algorithms, APIs, and everything outside this
admitted type slice is still hand-written.
