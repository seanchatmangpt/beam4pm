# The engine and ggen manufacture flow (explanation)

How beam4pm's application source comes to exist: an RDF graph, a
marketplace pack, one sync command, and a gate chain that refuses drift.
Understanding this flow explains almost every convention in the repo.

## The two engines

- **Rust ggen (Tera templates)** — manufactures `lib/` record types,
  Erlang `src/`, and Gleam sources from the `bpm:` vocabulary.
- **ggen_igniter (EEx)** — manufactures the Ash resources under
  `lib/beam4pm_ash/resources/` and the ingest router
  (`lib/beam4pm_ocel_ingest.ex` carries the "GENERATED by ggen_igniter"
  header).

Comparison and rationale: `docs/explanation/two-manufacturing-engines.md`.

## The inputs

- `ontology.ttl` — the repo's own RDF instance data (about 25.5k lines,
  742 `bpm:RecordType` declarations). This is the single source of truth
  for record types, fields, ingest routes (`bpmi:AdmittedIngestRoute`),
  and hand-authored-source admissions (`bpm:HandAuthoredSource`).
- `ggen.toml` — wiring: `[ontology] source = "ontology.ttl"` plus a public
  import closure (`prov-o`, `org`, `owl-time`, `sosa`, `ssn`, and the
  post-LLM runtime contract ontology), and the `[packs]` table pinning the
  vendored packs by path (`beam4pm-process-model`, `beam4pm-pro-infra`,
  `beam4pm-wasm-engine`, `beam4pm-pro-entitlement`,
  `github-actions-pack`).
- `vendor/ggen-marketplace/packs/beam4pm-process-model-pack` — the `bpm:`
  vocabulary and the code templates (a git submodule).

## The flow

```
ontology.ttl + pack templates
        |  ggen sync run          (just sync: rm -f ggen.lock; dry-run; run)
        v
lib/ src/ gleam/ schema/ docs/reference/   <- GENERATED, header-marked
        |  just verify            (submodules -> sync -> authorship ->
        v                          engine_dispatch -> lint_truth ->
                                   mixexs_defect_audit -> test)
green receipt
```

Provenance is per-file, signalled by a first-line `GENERATED by ggen ...
Do not edit.` marker — never by directory. There is no `generated/` dir;
manufactured code lives exactly where hand-authored code would
(`CLAUDE.md`, "What this repo is").

## Why the gates exist

Every gate in `just verify` converts one drift class into a refusal:

- `authorship` (`scripts/gate_authorship_check.sh`) — hand-authored code
  under `lib/` must be an admitted `bpm:HandAuthoredSource`, so a
  hand-edit of a generated surface cannot hide.
- `engine_dispatch` (`scripts/gate_engine_dispatch_check.sh`) — the WASM
  engine dispatch surface (`BeamPM.EngineManifest`, GENERATED from the
  WASM engine ABI graph) stays consistent with the engines' facades.
- `lint_truth` / `mixexs_defect_audit` — doc/truth linting and mix.exs
  defect audit.

The consequence: a change is either an ontology edit (regenerate), a
template edit (upstream + submodule bump), or a hand-edit of a legitimate
manufacturing input (`ontology.ttl`, `ggen.toml`, `scripts/`, docs). The
narrow receipted exception path for direct intervention on generated files
is documented in
`docs/jira/v26.8.29/03-architecture-and-ggen-manufacturing.md`.

## The engine layer below the code

Beyond code manufacture, beam4pm hosts WASM process-mining engines
(rust4pm, ferroplan, petgraph, tract). `BeamPM.EngineManifest`
(`lib/beam4pm_engine_manifest.ex`, GENERATED) is a runtime-reflectable
catalog of every engine and every JSON wire op, each op tagged
`consequence: :read | :do` — `:read` observational, `:do` mutating state
inside the engine's wasm linear memory. "Neither class is host authority"
(`@moduledoc`); calling still goes through each engine's own facade
(`BeamPM.Rust4PM`, `BeamPM.Ferroplan`, `BeamPM.Petgraph`, `BeamPM.Tract`).

## What this buys

- Regenerability: any generated file can be rebuilt from the graph, so
  drift is always fixable forward.
- Admission: new behavior either fits the vocabulary (becomes ontology)
  or stays thin hand-written orchestration (scripts/), never a silent
  third category.
- Replay: `just verify` is the same chain locally and in CI.
