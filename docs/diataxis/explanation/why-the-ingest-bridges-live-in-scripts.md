# Why the ingest bridges live in scripts/, not lib/ (explanation)

beam4pm has two hand-authored ingestion modules — `BeamPM.Ingest.Bridge`
(`scripts/ingest_telemetry.exs`) and `BeamPM.Evidence.Ex4pmBridge`
(`scripts/ex4pm_bridge.exs`) — and neither lives in `lib/`. This is not an
oversight; it is the repo's manufacturing doctrine applied consistently.

## The doctrine: source is manufactured, not written

Per `CONTRIBUTING.md`, most of `lib/`, `src/`, `test/`, and `gleam/` is the
output of ggen acting on `ontology.ttl` plus the vendored
`beam4pm-process-model-pack` templates. Every manufactured file carries a
`GENERATED by ggen ... Do not edit.` first-line marker, and
`scripts/gate_m2_check.sh` finds manufactured files by that marker — never
by directory. There are exactly two legitimate ways to change generated
code: edit `ontology.ttl` (instance data), or change the pack's templates
(upstream PR + submodule bump).

The ingest bridges are **not** expressible in that vocabulary. They are not
records with fields (`bpm:RecordType`); they are orchestration *behavior* —
telemetry handler attachment, ETS buffer management, envelope mapping,
refusal surfacing. Manufacturing them would require new template capability
for no vocabulary gain.

## The release rule

`scripts/` is a hand-editable manufacturing input. Concretely, this buys:

1. **No authorship gate exposure.** Hand-authored code that is *not* an
   admitted `bpm:HandAuthoredSource` under `lib/` would trip
   `scripts/gate_authorship_check.sh`. A script needs no such admission —
   the same placement rationale stated in the header comment of
   `scripts/ex4pm_bridge.exs`.
2. **Not compiled into the OTP release by default.** Script-defined modules
   load at runtime via `Code.require_file/1`, so a node that never attaches
   the bridges never carries them. This is why
   `lib/beam4pm_evidence.ex` (`ensure_ingest_bridge_loaded/0`) and
   `scripts/ex4pm_bridge.exs` (`ensure_loaded/0`) both exist: they require
   the scripts on demand, idempotently per VM run.
3. **Direct-call avoidance is a consequence, not a style choice.** Because
   `BeamPM.Ingest.Bridge` is runtime-defined, callers use
   `apply(BeamPM.Ingest.Bridge, :ingest, [event])` — a direct call would
   emit an "undefined module" compile-time warning. You can see this exact
   pattern in `lib/beam4pm_evidence.ex`'s `attach_all/0` and in
   `ex4pm_bridge.exs`'s `ingest_one/2`.

## The composition shape

The two bridges are the same pattern applied to two sources, over the same
generated capital:

```
source                     bridge (scripts/)              generated capital (lib/)
-------------------------  -----------------------------  ------------------------
:telemetry.execute/3  -->  BeamPM.Ingest.Bridge      -->  BeamPM.Types.OcelEvent.new/1
ash_ex4pm broadcaster -->  BeamPM.Evidence.Ex4pmBridge -->  BeamPM.Discovery.traces_from_events/2
```

Both converge on one bounded buffer (`BeamPM.Ingest.Bridge`'s ETS table,
oldest-drop at `:ingest_buffer_cap`, default 50,000) and one discovery
entry point. The hand-written layer is deliberately thin: mapping and
buffering only. Semantics — what an OCEL event *is*, how traces group —
stay in the generated, ontology-governed layer where they are admitted and
regenerable.

## Why the buffer is ETS, not a list

The first implementation buffered events in a `:persistent_term` literal
list: unbounded, O(n) per write (~397us at 2k buffered events), and a 20k
realtime run crashed the VM (`literal_alloc` + `erl_crash.dump`; see
`notes/ex4pm-realtime-audit.md`, cited in the header of
`bench/ex4pm_bridge_bench.exs`). The current design — a named, public
`:ordered_set` ETS table owned by a lazily-started GenServer, with an
atomic `:ets.update_counter/4` sequence row and oldest-drop cap — is
O(1) per ingest and survives caller crashes, because the table lives
outside the calling process (the same survival property `Ex4pm.Evidence.Store`
has). `scripts/ex4pm_soak.exs` and the bench are the standing evidence that
the fix holds.

## When a bridge should graduate into lib/

If a bridge's behavior becomes a fact about records in general (a new
constructor shape, a new projection), the right move is the pack-template
path (`CONTRIBUTING.md` section 1, option 2) — not moving the script. As
long as the modules are orchestration over already-generated capital, they
stay scripts: cheapest standing position, no admission needed, regenerable
capital untouched.
