# Elixir Example: OCEL Event Log Demo

## What this is

`ocel_log_demo.exs` is a real, runnable Elixir script exercising the
ggen-manufactured `BeamPM.Types.OcelEvent` module directly. It is not a mock,
not a fixture, and not a description of behavior -- it constructs three
`BeamPM.Types.OcelEvent` structs through the module's own `new/1` constructor
(the same constructor generated for every consumer of this type), and prints
a one-line summary of each event.

`BeamPM.Types.OcelEvent` is defined in
`lib/beam4pm_types.ex`, generated by `ggen` from the admitted
`bpm:RecordType` graph in `ontology.ttl` -- see the header comment in that
file (`# GENERATED by ggen ... Do not edit.`). This example never edits or
reimplements that module; it only calls it.

## What the script does

1. Builds three raw event maps with `:event_id`, `:event_type`, `:event_time`,
   and (for two of the three) an optional `:attributes` map -- the exact
   shape `OcelEvent.new/1` accepts.
2. Passes each map through `BeamPM.Types.OcelEvent.new/1` and pattern-matches
   the result:
   - `{:ok, event}` -- the struct is kept.
   - `{:error, reason}` -- the script prints the error to stderr and calls
     `System.halt(1)`, so a malformed event log fails loudly instead of
     silently producing partial output.
3. Prints one line per built event via `IO.puts`, showing `event_id` and
   `event_type`.

## Real invocation

This script must be run from the **beam4pm project root** (this repository's
top-level directory, the one containing `mix.exs`), because Mix resolves
`lib` (where `BeamPM.Types.OcelEvent` lives) via that
project's `elixirc_paths`. Compile the project first, then run the script
with `mix run`:

```sh
cd /path/to/beam4pm
mix compile
mix run examples/elixir/ocel_log_demo.exs
```

Expected output:

```
Built 3 OcelEvent structs via BeamPM.Types.OcelEvent.new/1:
  e-1001 :: PlaceOrder
  e-1002 :: PackItems
  e-1003 :: ShipOrder
```

This has been run for real against this repository's `mix.exs` (`app:
:beam4pm`, `elixirc_paths` including `lib`) with Elixir
1.19.5 / Erlang/OTP 28, producing exactly the output above.

## Why `mix compile` first, even though `mix run` compiles automatically

`mix run` recompiles a stale project on its own, so the explicit `mix
compile` step is not strictly required for a clean checkout. It is called
out here because this script depends on `BeamPM.Types.OcelEvent` being
resolvable at all -- if `lib/beam4pm_types.ex` is missing,
stale, or the project has never been compiled in this environment, `mix
compile` is the fastest way to surface that problem directly, before
attributing a failure to this example script instead of to the generated
module it depends on.
